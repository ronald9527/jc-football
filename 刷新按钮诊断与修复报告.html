一、问题与结论

用户反馈「刷新按钮还是没啥用处，按了还是旧数据」。逐层排查 按钮 → Cloudflare Function /api/refresh → GitHub Actions workflow_dispatch → 海外 runner 跑 run_daily.sh deploy， 结论不是「按钮没接线」或「PAT 失效」：按钮成功触发了 CI，但 CI 在海外根本跑不完。 竞彩官方接口 webapi.sporttery.cn 对美国机房 IP 恒定返回 HTTP 567， 主赛程虽能回退 500.com，但「赔率历史」逐场 30s 超时 ×30 场、「赛果回填」逐条 929 条 累计烧满 90 分钟，被 timeout-minutes 强杀（run cancelled）， 永远走不到「构建 + 部署」。前端又把「是否重载 / 是否成功」全赌在这个 run 上， 于是数据 updateTime 一直锁在旧批次，顶栏持续红字「非今日批次」。

四、修复项（一次做完整，治本不打补丁）

1前端·主路径重构
triggerRePull() 改为点击即同步：loadLiveDatasets() 拉取云端已部署的全部 20+ 数据源并即时重渲染，toast 明确显示「已同步云端最新数据（更新于 X）」，2.6s 后带时间戳硬重载绕过 WebView/PWA 缓存。这一步 100% 可靠、秒级、必成功。
2前端·CI 降级
触发 /api/refresh 降级为 fire-and-forget 后台补充：不阻塞主路径、不轮询 run_id、绝不因失败/取消/超时报错。保留 version.json 变化监听，后台真产出了新部署就自动再同步一次。无论 CI 成功/失败/取消/超时/无 runId，都有确定性兜底，绝不再卡成「没反应」。
3抓取·官方接口熔断
fetch_daily.py 新增 _OFFICIAL_DOWN 熔断：主赛程一旦确认 567 回退 500.com，后续赔率历史/支持率/赛果回填等所有 sporttery 官方请求由 fetch() 瞬时短路，不再逐场 8 次重试 × 30s。CI 从 90 分钟超时压缩到数分钟跑完。本地中国网络官方接口 200 永不触发，行为零变化。
4抓取·回填提速
修正「已有赛果仍为补半全场结果逐条重查官方接口」的低效逻辑：实测 history.json 798 条已有赛果的记录 hitFlag/hhadResult 齐全（缺 0），一律跳过网络请求，只处理真正未开奖的记录。
5CI·配置修复
daily.yml：cancel-in-progress:true 清理排队僵尸 run；job 超时 90→40 分钟、step 级 30 分钟；新增 JC_FETCH_WALL_SEC / JC_FETCH_TIMEOUT 双墙钟；移除 push 自动触发（源码提交不再拉起海外残缺抓取）；保留定时与手动 workflow_dispatch。
6部署·残缺守卫
run_daily.sh 新增守卫：CI 环境 + 本轮官方接口熔断（.ci_official_down 标记）→ 跳过部署，防止 500.com 的 30 场残缺数据覆盖生产 59 场完整数据 + 赛果回溯 + 各类统计。这是过去每轮 CI 都必须人工 cancel 的根本原因，现自动化为安全护栏。
7验证·接线
selftest.py 新增 check_refresh_chain() 与流水线护栏校验；test_refresh_button_ui.py 让 /api/refresh 永不返回以模拟最坏 CI，验证按钮主路径不受影响。

五、验证口径

· 按钮主路径：拦截并让 /api/refresh 永不返回（模拟 CI 90 分钟超时）， 按钮仍在 1.4s 内发起对 matches.json / version.json / vzhan_data.json 等 云端数据源的拉取、即时给出「已同步…（更新于 X）」反馈、按钮恢复可点、无负面报错。
· 自检：selftest.py 新增 check_refresh_chain()，校验前端不再赌 CI、 后端函数仍触发 dispatch、CI 清队列 / 去 push / 墙钟 / 残缺守卫齐全。
· 诚实边界：海外 CI 拿不到中国竞彩官方接口，本就在架构上无法独立产出「完整」数据； 因此「数据保鲜」由本地全量刷新 + 部署负责，按钮负责「把云端最新数据即时同步到手机」。 CI 触发仅作尽力补充，且加了残缺守卫，绝不会再用 30 场覆盖生产 59 场。
