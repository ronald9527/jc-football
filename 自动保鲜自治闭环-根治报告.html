用户诉求（原话）：
「往后不要让我再提醒了，自动的落实这些东西，不要踢一脚做一步，不提醒就什么都不做」
本次不新增功能、不降低任何推荐门槛，只解决一件事：让系统自己巡检、自己发现问题、自己修、自己上线、自己留痕，不再依赖用户发现异常后开口提醒。

一、根因取证：不是「今天没新数据」，是自动任务根本没跑

证据实测值结论
自动任务 #14693059 status0（文档定义 1=启用 / 0=停用）任务被暂停
lastRunAt2026-11-12 16:59:41，距排查时 14 小时 40 分14+ 小时一次都没跑
线上 version.json.updateTime排查时仍为 2026-11-13 04:09:00，到 07:39 已 3 小时 23 分未推进用户看到「一直不更新」
旧任务指令形态5 步自然语言「下载代码 → 重建凭证 → 对齐节流 → 跑流水线 → curl 看一眼」，第 5 步只核对、不判定、失败只「如实汇报」即使跑了也不会主动发现逻辑退化

也就是说：用户不提醒，系统既不会动，也不会发现自己没动。这是「踢一脚做一步」的真正来源。

四、每轮自动做的 12 项健康巡检

  • 主批次是否等于权威竞彩当天（防时钟漂移 / 跨天不推进，beijing_clock 用 HTTP Date 校准）
  • 分层串关是否死锁（≥2 条合格却 0 档 → 结构性缺陷，不是「今天没好比赛」）
  • V站 一等字段合并覆盖率、日期索引含当天、非法 utcDate = 0
  • 串关历史顶层统计与 records 实算一致、篮球历史已结算凭证与日期覆盖未缩水
  • ab_stats 云端可用、无空壳专家文章、数据新鲜度
  • 线上/源码版本一致、串关逐腿证据完整（赔率≥1.6、样本≥20、超额≥0）
发现异常 → L1 秒级定点自愈（重合并 V站 / 对齐统计 / 清空壳 / 重建 ab_stats / 历史对账）→ L3 每轮必跑全量刷新+部署 → selftest 护栏 → L2 强制上线 → 线上复验 → 写状态留痕。

六、过程中真实抓到并修掉的两个问题

问题处理

这两个都是护栏自己抓出来的——正是「以后不再出错」要的效果：问题在无人提醒时被自动发现并自动修正。

七、边界（如实说明，不夸大）

  • 数据无变化时如实标记 NO_CHANGE，绝不伪造 updateTime；但每轮仍真实巡检、真实留痕，用户能看到系统确实跑过。
  • 推荐门槛（赔率 1.6~3.2、实证超额≥0、样本≥20、非平局、真实 EV、同批次）一个都没放宽。
  • 线上分层串关当前显示本来就正常（前端读 batches[0]，字段完整）；本次加的锁定态文案是防御性修复，针对顶层字段被直接用作渲染源的旧数据形态，不改变当前显示。
  • 连续自愈仍不健康会标 BLOCKED 并逐条列出未修复项；数据源临时不可用时流水线内置降级处理，绝不把残缺数据覆盖到生产。

八、以后会自动发生什么（不需要你再说一句）

  1. 每小时整点，自动任务自举后调 auto_pilot.py，做完全部巡检与刷新。
  2. 任一模块悄悄退化（主批次错一天 / 串关死锁 / V站 丢失 / 统计不一致 / 历史缩水 / 空壳文章），当轮自动发现、自动修、自动重新部署、自动复验。
  3. 打开 /version.json 能看到 lastPatrolAt 与 patrolHealth；打开 /auto_pilot_status.json 能看到 13 项逐条结论与本轮动作。
  4. 打开 App 若发现数据陈旧，页面自己静默触发一次保鲜并自动同步，无需点「刷新数据」。
  5. 任何一层被改回去或停摆，自检「检查 16」立即报 ERROR，不会悄悄坏掉。
